# opacity=0 让 RealityKit 停渲染，转场渐入首帧重建 GPU 资源阻塞主线程

日期：2026-11-20 · 票：096 · 状态：已修复并实测验证

## 前因

096 六段转场录屏取证里，token1（sky→solar）、token2（solar→earthOrbit）、
token6（solar→sky）的 `scale.transition end` 只有 **2 个采样**（首帧 + 末帧），
0.45s 窗口实际耗时 0.85–0.92s；逐帧亮度显示这三段是**单帧跳变**而非渐变。
其余三段（earth↔tiangong、earth→solar）28–29 采样、画面多帧渐变，正常。
尺子读数「单调插值」在这三段名存实亡——只有首尾两个值。

## 排障过程与误判

1. 先怀疑 XCUI 查询阻塞主线程 → 把段间稳态从 2s 拉到 6s，**无效**（仍 2 采样）。
2. 怀疑录屏帧率/对齐错误 → 查明 simctl 录屏是可变帧率（nominal 18fps），
   且 `video-start-ms` 符号传反（应传「录屏第 0 帧对应的 app 时钟」= 负偏移），
   修正后 NFR-12 判定的窗口才落在正确帧上。这是取证工具 bug，不是 app bug。
3. 怀疑 solar 场景重（480 粒子）→ 但 token5（earth→solar，solar 渐入）29 采样正常，
   **推翻**「场景重就卡」。
4. 加 `SPACEWALKER_TICK_DIAG` 逐 tick 日志：`applyMs` 全程 0.1–0.5ms，
   卡的是 **tick 之间的 gap（846/919ms）**——主线程被一次性长任务占住，
   不是每帧慢。推翻「apply 插值太贵」。
5. 归纳规律：卡的三段 from∈{sky, solar} 或 to 层**久未渲染**；
   不卡的三段入场层都刚渲染过。形成假设：**opacity=0 的 RealityView 被
   RealityKit 停渲染并回收 GPU 资源，渐入首帧重建资源阻塞主线程**。

## 本质

`ContentView.layer()` 与 `ScaleTransitionEngine.opacity(for:)` 对非当前层
返回 opacity=0。RealityKit 据此暂停渲染；转场把某层从 0 渐入时，首帧要
重新上传 mesh/编译 material，模拟器上阻塞主线程 0.8–0.9s，ticker 停摆，
插值只剩首尾两点。boot 后首次访问的层（solar/earth）与久离的层（sky）必中；
刚渲染过的层（token4/5 的 earth/solar）不中。六段现象全部解释，无一反例。

## 证据

- 诊断日志（修复前）：token1 `gapMs=846.3 applyMs=0.5`、token2 `gapMs=919.0 applyMs=0.4`，
  均 samples=2；token3/4/5 gap≈16ms、samples=28–29。
- 修复：非当前层与渐入层 opacity 下限改 **0.002**（深色背景不可察觉，GPU 资源常驻）。
- 修复后同脚本同环境重跑：六段全部 **samples=28–29、violations=0**，
  avg 29.5–59.5（模拟器 + 录屏 + XCUI 三重负载）。

## 代价

约 35 次工具调用用于排障（含 3 次错误假设、2 次取证工具自身 bug 修复、
1 次抽帧进程卡死重启）。其中「先复算对齐符号」这一步本可在第一次 NFR-12
判定前做，省约 8 次调用。

## 影响

- 096 转场视觉连续性恢复；FR-L-04 尺子插值在所有六段真实生效。
- 四层常驻持续渲染增加 GPU 负载；模拟器实测可接受，真机帧率留 M4 门禁复测。
- 取证脚本新增 tick 诊断开关与对齐修正，097 导览录屏复用。

## 如果重来

- 看到「采样数=2」先查 tick 间隔分布，而不是先调稳态时长。
- 取证工具的对齐公式先用一次已知事件（tap）交叉验证符号与量纲，再跑判定。
- 「opacity=0 是否停渲染」这类平台行为，直接做 A/B 实验（0 vs 0.002）比归纳推理快。
