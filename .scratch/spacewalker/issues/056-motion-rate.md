# 056 姿态采样率：配置 60Hz，实测 33Hz

- 日期：2026-11-07
- 状态：已定论（不改代码）
- 关联：FR-B-02、M2 门禁（v0.7 新增「姿态跟随无跳变」）

## 一、现象

`DeviceAttitude` 配 `deviceMotionUpdateInterval = 1/60`，日志 `sky.motion started intervalMs=17` 也对得上，但 `sky.motion rate` 稳定报 **33–34**。历史记录里写的是 67Hz。

## 二、排除法

| 假设 | 实验 | 结果 |
|---|---|---|
| XCUITest 拖慢了主线程 | 不带 UI 测试、`devicectl` 直接启动，采 27 个窗口 | **33.1 Hz**（min 33 / max 34），渲染 60.3fps 无卡顿 ⇒ 排除 |
| 帧率掉导致回调被合并 | 同期 `sky.perf` | avg 60.3 / hitch 0.0% ⇒ 排除 |
| CoreMotion 有 33Hz 硬顶 | 把请求改成 1/120 重测 | **100 Hz**（min 100 / max 101）⇒ 排除，设置是被尊重的 |

## 三、定论

`1/60 → 33Hz`、`1/120 → 100Hz`，非单调。CoreMotion 对请求间隔做了量化，60Hz 这个档位在这台机器上落到 33Hz。这不是本次重构引入的，是一直如此，历史里的 67Hz 大概是旧机型或不同 iOS 的读数。

## 四、为什么不改

- 准星停留是 0.6 秒判定，33Hz 一秒给 30 多个样本，够用；`DwellSelector` 的 0.1s 单步上限也不受影响。
- 要拿到 60 以上得请求 1/120（实测 100Hz），代价是两倍的姿态回调与平滑计算，而 054 刚验过 thermal 全程 nominal——没必要为了一个没被抱怨的观感去换发热。
- 真要做也该先有「转向时肉眼可见台阶」的证据，现在没有。

## 五、如果将来要动

先量三件事，再改参数：转向时的角度台阶（相邻帧朝向差）、GPU 与 CPU 占用、10 分钟 thermal。`1/90` 可能落在 60 附近，比 1/120 便宜，值得先试。
