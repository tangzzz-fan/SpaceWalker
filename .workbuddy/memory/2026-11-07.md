## 技术路线调研结论

- iOS 26 起官方主推 `RealityView` + `SpatialTrackingSession`：默认会话已包含 camera/world/plane/object/image/face 追踪与 occlusion/shadow/collision/physics，`camera: .back` 提供相机背景；`run(configuration)` 返回 `unavailableCapabilities` 用于降级。
- WWDC25 新增可用交互积木：`ManipulationComponent`（免手写拖拽/缩放/旋转）、`MeshInstancesComponent`（海量实例）、`EnvironmentBlendingComponent`（现实遮挡）、`ARKitAnchorComponent`（直取 ARKit transform）。
- 兼容备选为 `ARView` + ARKit（资料多、可下探 iOS 18，但手势/锚点要自己写，且用不上新 API）。
- 边界：AR 能力**无法在模拟器验证**，编译通过不等于真机可用；真机需 iPhone（用户设备 iOS 26.6 满足最低要求）。

## 姿态跟随修复：方向错 + 抖（真机确认解决）

- 症状：转头方向相反、星空剧烈抖动、不跟随。
- 根因 1（方向）：CoreMotion 参考系 Z 朝上、RealityKit 世界 Y 朝上，原实现用 `(x, z, y)` 分量交换 —— 这是**反射矩阵**（det=-1），水平镜像。正确换基是 `(x, z, -y)`，等价绕 X 轴 −90° 纯旋转。
- 根因 2（抖）：姿态被拆成 `yaw=atan2(x,-z)` + pitch，接近天顶时 1/cos(pitch) 发散；且 30Hz 定时器 → `@State` → SwiftUI body → `RealityView.update` 写实体，与 60Hz 渲染不同步。
- 修法：完整四元数（含 roll）直驱 `root.orientation=inverse(deviceToWorld)`；67Hz 运动回调内直写实体，不经 SwiftUI；20ms 球面平滑；用 `motion.gravity` 运行时校验四元数约定（两候选取满足 R·g=(0,-1,0) 者），日志只判定一次未翻转。
- 顺手修复：`pick` 一直用**局部坐标**投影，根节点旋转后点击全错；改 `root.convert(position:to:nil)`。
- 真机证据：rate 66–67Hz，`fwd` 从 (0,-1,0) 平滑扫到 (0.61,-0.36,-0.70)，人工确认跟手不抖。
- 删除 `SkyRig.aim`（拆 yaw/pitch 的旧路径，无生产调用点），仿真器降级只留 drag。

## M2-024 今夜此刻（FR-B-05）

- **前置缺陷**：`StarField.direction` 用 `(x,z,y)` 轴交换，等价对物理右手系做一次反射（`RA0 × 北极` 应为 `-RA6h`，原实现给 `+RA6h`）。单星无感，但对齐真实天空会得到镜像星座，且反射无法用四元数表示。修法：`z = -cosδ·sinα`，加"基向量叉积 = -1"单测。

## 032/033 时间滑块诊断 + 开源内容源调研

- **时间滑块抖动的五个成因**（全部在 `eba3e50` 代码里核实）：① 未开「今夜」时 `applyAlignment` 因 `guard observer.isOn else { return }` 直接返回，`field` 恒 identity，拖滑块星空完全不动——这是"大跳变"的真凶；② 同一个 `alignmentStamp` 1 秒节流同时管住时间路径与 67Hz 运动回调，拖动期间几乎每次 `onChange` 都被吞，只剩每秒一次阶跃；③ `shiftedNow()` 每次 `Date()` 重采样，时间基准随时间漂移；④ `step: 0.5` = 7.5°，140pt 宽滑块每 2.9pt 跳一大格；⑤ `timeOffset` 是 `SkyView` 的 `@State`，拖动时整棵 body（含 `RealityView.update`、`skySubtitle` 里的 GMST）每秒重建 60 次。
- 方案分层：A 拆 `refreshField()` 无节流 + 运动回调不再调用；B `timeBase` 固定基准；C 赤道模式也让时间生效（绕天极 -15.041°/h）；D 步进换挡 + 时刻显示 + 播放（1×/60×/600×）；E 订阅粒度下沉到 `TimeScrubber` 子视图。不做插值平滑。
- **星官全表可用**：`Stellarium/stellarium-skycultures` 的 `chinese/` 目录，318 官 / 312 有连线 / 1385 颗 HIP 成员星 / 315 中文名 / 240KB。仓库根是 AGPL，但该目录 `description.md` 第 258 行显式声明 **Text and line: CC BY-SA**、两张古图 PD，与现有 HYG CC BY-SA 兼容。其它文化目录（如「西游记」CC BY-NC-ND）不可碰。

## 061 星官抢占星座识别（两层根因）

- **第一层：优先级设计错误**。059 把星官塞进与星座同一个互斥槽位且给了更高优先级。猎户座中心必然落在参宿里 → 每 80ms 一次 `clear(.constellation)` 把轨道按回零，`advance` 里 `track.target != target` 重建 Track，`elapsed` 永远到不了 0.6s。A/B 实测：culture=1 只有 `sky.asterism dwell=参宿`，culture=0 才 `sky.constellation dwell=Ori`。修法：星官只在 constellation 与 pattern 都未命中时参与；门控下沉到 `SkyScene.Candidates.forAttention(cultureEnabled:showsConstellations:showsPatterns:)` 可单测。同时补 050 遗留：constellation 候选此前不受 showsConstellations 门控。`SPACEWALKER_NOCONST=1` 提供无头验收入口。
- **第二层：轮廓边界点被判在外**。修完优先级后真机仍有 asterism 出现。量化：Ori 9 颗成员星只有 3 颗判在自己的轮廓内，Cyg 5 颗只认 1 颗。原因是 `OutlineShape.contains` 用标准射线法，**轮廓顶点本身在边界上，归属不稳定**。修法：`edgeTolerance = 0.02`（归一化坐标），点到任一边在容差内即命中。修后 Ori 7/9、Cyg 5/5、Ser 5/5。
- 回归测试：遍历 88 个星座全部轮廓顶点，断言每个都判在自己区域内（修前红，修后绿）。333 项全绿。
- 星官信息不丢：`AsterismField` 增 `constellation` 字段，星座卡多一行「星官：参宿 · 伐（附参宿）」。截图确认。
- 顺手修：`asterismFields` 原建在 `guard !segments.isEmpty … else { return }` 之后，星表为空/无连线时索引整块不建。
- **待决**：星体优先级最高，准星落在亮星上时星座轮廓不亮（Cyg 瞄中心 → Sadr，Cas → Cih）。高亮是不同粒度、本不该互斥；卡片才该唯一。是否做「高亮分层 + 卡片唯一」需要产品决策，未动。

## 064 旋转体与三段实验舱（已完成）

**先定案再动手**：`dockingPortZ` 是玩法参数（`TiangongSession:278` 用它算飞船位置，2cm 轴向容差量在它上面）。

`frustum` 退化成两点特例。

**三个真 bug，两类工具各抓到一个**：
1. **母线坐标顺序反了**（数据写 `(t,r)`、消费端读 `(r,t)`）→ 返回舱细到看不见。被
   `testCapsuleProfileShrinksMonotonically` 抓到。**这是写断言而不是只看截图的直接收益。**
2. **端盖复用了侧面法线** → 中心法线与环法线插值，渲染出一圈星芒。修法：端盖另起一组顶点，法线统一 ±Y。
3. **共面封盖 z-fighting** → 锥段与相邻圆柱端盖同平面，出现放射状锯齿。加 `Caps` 枚举，贴合端留空。
   这条在截图上极容易被误判成"破面"，本质是深度冲突。

**取证手法**：灯光太暗、截图看不清接缝，于是**不靠截图**——`TiangongSceneSegmentationTests` 直接量
四个子件的轴向区间，断言首尾相接误差 < 0.2 mm。这比目视硬，也不受光照影响。
