## `/to-spec` 的测试缝调研（待董事长确认）

- 现状：`ContentView` 按 `AppState.route` 硬切三个 View（无 TabView），顶部状态卡与底部图标栏都是各 View 里的 private var；`Tests/` 15 个 XCTest 文件**零 UI 单测**，只有 `UITests/LandscapeUITests.swift` 做存在性断言 + 截图存档（不比对）；`docs/gates/` 靠人工截图/日志。
- 界面决策全埋在 View body 的 `if` 里（天宫 `labelLayer` 常驻 5 标签、三处 `#if DEBUG` fps/probe 渲染、各 controlBar 写死的 5–9 个图标），没有可查询的等价状态 → 重构后无法自动回归。
- 提案（**唯一 seam**）：在 `AppState` 加 Equatable 值类型 `ChromeState`，字段为 `route / primaryAction / contextControls / statusLine / debugOverlay / visibleLabels / infoCard`，由纯函数 `ChromeState.derive(...)` + `makeAppReducer()` 统一重算；View 改为只读渲染；复用 `TestStore` 断言「3 个带文字 tab、主操作唯一且在底部、≤3 控件、零调试文案、选中才出标签与信息卡」。像素/布局仍由 XCUITest 截图兜底。
- 关联：`LaunchMode.initialRoute` 默认路由要从 `.solarSystem` 改 `.sky`；`SPACEWALKER_FLAG_*` 直接读 `ProcessInfo`，与 LaunchMode 的字典注入不统一，spec 里要定一个唯一开关来源。
