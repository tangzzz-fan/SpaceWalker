## A2 iPad 边界 —— 拟定：iPhone-only（`TARGETED_DEVICE_FAMILY: "1"`）

**产品依据**：PRD-UI 用户画像写明「夜里、床上、通勤，单手操作」——这是 iPhone 姿态场景。
星图核心交互是「转动手机环顾」（CoreMotion 姿态跟随），iPad 双手持握转 90° 的体验不成立；
天宫对接的捏合/双指手势也按单手可及设计。iPad 不是「多一个屏幕」而是「换一种交互」。

**工程依据**：全仓无任何 iPad 版式代码（无 idiom 分支、无 sizeClass 适配）、
无 iPad UI 测试、080 门禁只取 iPhone 数据。保留 `"1,2"` 意味着上架要补
iPad 13" 截图（2064×2752）+ 版式验收 + 盲测重跑——为零收益场景付三套取证成本。

**代价**：iPad 用户无法安装（App Store 会显示「仅 iPhone」）。可接受：目标用户画像不含 iPad。
**反方**：若未来想做 iPad「桌面星图」模式，届时改回 `"1,2"` 并补版式即可，现在不预支。
**附带澄清**：横屏保留——043 票有意实现（LandscapeUITests 在测），不是漂移；
PRD-UI「竖屏」措辞需回写为「竖屏为主，横屏为 043 既有能力」。

**实施**：project.yml 改 `"1"` → xcodegen → 全量回归 → APPSTORE.md 删 iPad 截图项 → PRD-UI 回写。

## A4 帧率「下限」口径 —— 拟定：30s 稳态窗口内 avg 快照的最低值（窗口口径）

**这是七项里唯一影响门禁结论的裁决，必须最严谨。**

**PRD 原文**：NFR-01「A/B 平均 ≥55fps、下限 30fps；C 平均 ≥25fps、下限 20fps」，
取证方式「真机 30s 录屏 + 帧率统计」。「平均」与「下限」并列，且取证是 30s 窗口——
**「下限」的自然语义是窗口统计的下限，不是单帧极值**。

**为什么排除「最慢单帧」**：
- 现有数据 B min=6.6、C min=12.0，若按单帧口径两阶段全不达标——但 thermal 全程 nominal、
  avg 59–60，这是**采样瞬时抖动**（HUD 快照与渲染帧不对齐、系统后台抢占），不是持续掉帧。
- 单帧口径在 iOS 上不可达：任何 App 都会被系统中断打出单帧低谷，
  按此口径全行业无 App 能过 60fps 门禁。判据若不可达，等于没有判据。
- PRD 写「30s 录屏 + 帧率统计」而非「逐帧分析」，取证手段本身就指向窗口统计。

**为什么选「窗口 avg 最低值」而非「窗口 avg 均值」**：
- 均值口径太松：B 均值 58.93 但最低 55.4，C 均值 59.83 但最低 26.8——
  均值会把 C 的 26.8 低谷藏掉。下限取最低值才真正守住「最差 30s 也不崩」。
- 该口径下现有参考数据：B 最低 55.4 ≥ 30 ✓、C 最低 26.8 ≥ 20 ✓，**两阶段达标**。
- 同时保留 avg 均值 ≥55/≥25 的独立判据（B 58.93 ✓、C 59.83 ✓）。

**代价**：C 的 26.8 距 20 只有 6.8 余量，若后续几何加重可能击穿——
这正是下限该起的预警作用，不是口径问题。
**反方**：若董事长认为 26.8 不可接受，可收紧为「P5 百分位 ≥30/20」，
但需重新取数（现有日志只有 avg/min 快照，无逐帧分布），且 C 大概率不达标需优化。
**不建议**：最慢单帧口径（理由如上）。

**实施**：runbook §6 勾选「30s 窗口统计」+ 写明「下限 = 稳态窗口 avg 快照最低值」；
参考数据按此口径预判 B/C 达标（**最终判定仍归人工签字，agent 不代判**）。

## A5 iOS 27.0 等价性 —— 拟定：接受等价，参考数据可转正（附条件）

**依据**：
- 基准 26.6 与实测 27.0 同为 iPhone 16 Pro（iPhone17,1），硬件完全一致。
- iOS 26→27 是同代际小版本，RealityKit/Metal 渲染管线无破坏性变更；
  thermal 全程 nominal 说明无新系统级热节流。
- 帧率瓶颈在 App 自身几何与 draw call，不在 OS 版本——同硬件同代码，
  27.0 的数据对 26.6 有强代表性。

**附条件（必须写明，不是无条件接受）**：
1. 转正数据须用**新 bundle id `com.tango.xingcha` 的包**重取（旧 id 数据容器不互通，
   且 081 删按钮后代码已变）——现有参考数据是旧 id + 旧代码，**不能直接转正**，
   只能作为「口径验证参考」。
2. 若 26.6 真机可借到，优先补一组对照；借不到则接受 27.0 单组 + 上述条件。

**代价**：无 26.6 对照，审核若问「为何基准 26.6 实测 27.0」需解释（小版本等价，行业惯例）。
**反方**：若董事长坚持 26.6 基准，需找一台 26.6 设备（iPhone 16 系列出厂 26.x，
未升级的机器），agent 无法凭空造出。

**实施**：runbook §6 勾选「接受」+ 附条件注记；D5 真机接上后用新包重取 B/C 两段。
