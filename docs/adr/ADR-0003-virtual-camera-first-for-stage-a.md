# ADR-0003：A 阶段默认虚拟相机，平面锚定降级为可选入口

- 状态：已采纳（2026-11-07）
- 取代：无（修订 ADR-0001 的适用范围，不改其技术结论）
- 关联：PRD v0.5 §7.2、§10；ticket 021；`docs/assets/NASA-ASSETS.md`

## 背景

A 阶段原设计是「把太阳系放到真实桌面上」。M0 已把这条路验证成立：平面锚定、命中放置、能力矩阵、权限门控、60fps 全部有真机证据。

但产品侧出现一个更根本的问题：太阳系放在真实房间里**不好看**。白墙与杂物构成背景、环境光过亮、行星只是几个小球、轨道线被现实纹理淹没；而真正的空间感来自尺度对比与公转运动，不来自"它在我桌上"。

同时统计了 A 阶段的 7 条功能需求：只有 FR-A-01（平面放置）与 FR-A-07（桌面边界）依赖桌面，其余 5 条与桌面无关。

## 决策

A 阶段默认走 **`camera: .virtual` + 星系天空盒**，不启动 ARKit、不请求相机权限；平面锚定保留为「放进房间」的可选入口，代码不删。

天空盒使用 NASA/Goddard SVS《Deep Star Maps 2020》4096×2048 等距柱状图（公有领域），构建期由 OpenEXR 线性 HDR 转换为 sRGB JPEG；加载失败回退到程序化星系。

## 理由

1. **可读性**：黑底 + 真实星场让行星边缘与轨道线清晰；真实房间会让同一套内容变成"贴纸"。
2. **验证成本**：虚拟相机不依赖 ARKit，**可在 iOS 模拟器完整验证**。此前每轮改动要走 build → install → launch → screenshot → 导日志四到五次真机往返，现在是本机一条命令。这一条的实际收益最大。
3. **iOS 能力缺口被 SDK 补齐**：`.realityViewCameraControls(.orbit)`（iOS 18+）提供相机绕目标点旋转，正好绕开 `ManipulationComponent` 仅 visionOS 的限制，也消除了 003 里"屏幕右 = +X、转向后失准"的手写映射问题。
4. **风险不增加**：M0 已经证明 AR 路径可用，A 转虚拟是产品取舍而非技术退守；B 阶段仍走全 AR。

## 后果

正面：

- 默认路径零权限、零 ARKit、零漂移；A 阶段不再被平面检测与漂移问题阻塞。
- 模拟器可验证，回归成本下降一个数量级。
- 真实星空替代程序化噪点，观感直接到位。

负面与约束：

- 产品第一印象从"AR 应用"变为"3D 应用 + AR 可选"；1.0 演示里的 AR 感要靠「放进房间」入口保住。
- B 阶段的 AR 风险只是推迟，没有消除。
- 天空盒 4096×2048 JPEG 4.5MB，模拟器冷加载 868ms（真机待测）；需要关注首帧时间。
- 相机由代码控制的 `PerspectiveCameraComponent` 驱动，仰角/距离必须夹取，否则会穿到轨道面以下。

## 赌注与止损

- 赌注：**用户更在意"看得清太阳系"而不是"它在我桌上"**。
- 验证方式：A 阶段首屏 10 次真机记录，问一句"你会想把它放到桌上吗"。
- Kill criteria：若 ≥ 6/10 的人第一反应是"想放到桌上"，或 AR 入口点击率 > 50%，则把 A 阶段改回相机优先，虚拟视图降为可选背景。

## 替代方案

- **相机 + 相机锚定（无平面）**：保住 AR 感，去掉平面临界风险；但没有地面参照、内容漂浮、光照不匹配，且仍无法在模拟器验证。否决。
- **纯虚拟、删掉 AR**：最省事，但会让 B 阶段从零开始，且丢掉 M0 全部成果。否决。
- **保持原状（桌面锚定优先）**：A 阶段会被平面检测与漂移问题持续拖慢，且观感更差。否决。
