# M2 / 全图层真机负载证据（2026-11-07 23:00）

| 项 | 内容 |
|---|---|
| 设备 | iPhone 16 Pro（iPhone17,1），iOS 27.0（24A437） |
| 构建 | Debug 1.0(1)，`SPACEWALKER_MODE=sky` |
| 图层 | 连线 138 段 + 轮廓 15 个面 + 星官 814 段 + 星群 98 段（全开） |
| 执行 | agent 自驱动：`devicectl` 启动 / 取日志 / 截屏；无需人工举机 |

## 1. 帧率

四组独立启动，每组采样 22 秒，读数取最后三个 5 秒窗口（`sky.perf`）：

| 朝向 | avg fps | min fps | 卡顿比 | 热状态 |
|---|---|---|---|---|
| 默认（未定向） | 58.5 / 59.0 / 60.0 | 28.2–34.2 | 1.7% → 0% | nominal |
| 猎户座（AIM=Ori） | 59.0 / 59.5 / 58.5 | 30.3–34.5 | 0% | nominal |
| 天蝎座（AIM=Sco） | 60.2 / 59.6 / 59.8 | 29.4–46.1 | 0.8% | nominal |
| 大熊座（AIM=UMa） | 59.8 / 60.0 / 58.5 | 28.4–38.5 | 0–1.7% | nominal |

结论：**五层全开在 A17 Pro 上稳在 58.5–60fps，像素填充率不是瓶颈。**

`min fps` 的 28–34 不等于「掉到 28 帧」，它是 120 帧窗口里最长的那一帧（约 35ms）。卡顿比 0–1.7%，对应 2 秒里偶发 0–2 帧。判定线是 avg ≥ 55、hitch < 2%，全组通过。

场景预算与模拟器一致：

```
sky.budget entities=16 meshes=12 constellation=138 asterism=814 pattern=98
```

16 个实体、12 个 mesh 也解释了为什么不怕：几何量级很小，之前担心的「节点太多」不成立。

## 3. 三个新发现

**① 星卡与星座卡会同时堆叠。** 猎户座那张截图里，「猎户座」标识卡和「Hatsya」星卡上下同时占掉半屏。代码上两者互不排斥：星卡由 `selected` 驱动、星座卡由 `identifiedConstellation` 驱动，谁后触发谁不覆盖谁。真机上很容易复现：先对准一颗星出卡，再移开一点点——准星还在轮廓里、但已经没有星，于是第二张卡叠上来。

**② 航向仍是缺的。** 开定位后顶栏显示 `31.3°N 120.6°E · 恒星时 32.5°`，但下一行是：

```
今夜此刻 · 时间已对齐，磁力计精度 25° 不足以定位（试试画 8 字或离开金属）
```

日志同样记录 `sky.align heading=-1.0 mag=25`。也就是说：纬度与恒星时对了，**方位还差一脚**，要靠「手机水平朝正北时点此」或「以某颗星校准」补。这是 FR-B-05 的已知边界，但它决定了「举起来对不对得上真实天空」这件事能不能验收。

**③ 不开定位时是另一个模式。** 顶栏明确写「赤道坐标（未对齐今夜）」，此时星图是赤道坐标下的虚拟天球，不能拿去和真实天空比。

## 4. 复现方式

```bash
tools/device.sh run --build            # 装包并以全图层启动
tools/device.sh log --grep "sky\."     # 跟随日志
tools/device.sh shot /tmp/a.png        # 真机截屏
```

不带参数启动也能拿到数据：Debug 构建默认写 `sky.perf`（`SPACEWALKER_FPS=0` 才是唯一的关闭方式），`SPACEWALKER_FPS=1` 只额外决定要不要在屏幕上显示读数。
